Introdução ao Controle de Versão e ao Git

Controle de versão é uma forma organizada de registrar a evolução de arquivos ao longo do tempo. Em um projeto de programação, ele permite consultar alterações, identificar quando elas foram feitas e recuperar versões anteriores quando necessário.

O Git é um sistema de controle de versão distribuído. Em vez de criar cópias manuais como projeto_final, projeto_final_agora_vai e projeto_final_v3, o projeto mantém um histórico de registros chamados commits. Esse histórico ajuda a entender o desenvolvimento e facilita a colaboração, desde que as alterações sejam organizadas e revisadas corretamente.

1. Instalando o Git

O Git precisa estar instalado no computador para que os comandos estejam disponíveis no terminal. No Windows, acesse a página oficial, baixe o instalador e siga as etapas. Para uma instalação inicial, as opções padrão costumam ser suficientes.

Acessar a página oficial de instalação do Git

Depois da instalação, abra um terminal — por exemplo, o Terminal do VS Code, PowerShell ou Git Bash — e execute: 

git --version

Esse comando mostra a versão instalada. Se o terminal informar que o comando não foi encontrado, verifique a instalação e abra um novo terminal.

2. Configurando nome e e-mail

O Git registra um nome e um e-mail como autoria de cada commit. Configure esses dados antes de criar o primeiro registro. Use o nome que deseja associar ao seu trabalho e, se quiser que os commits sejam associados ao seu perfil do GitHub, utilize um e-mail verificado na conta ou o endereço privado fornecido pelo GitHub.

git config --global user.name "Seu Nome Completo"
git config --global user.email "seu.email@exemplo.com"

Substitua os exemplos pelos seus dados reais. A opção --global aplica a configuração ao usuário do computador, para os repositórios que não tenham uma configuração local diferente.

Para conferir o que ficou configurado, execute:

git config --global user.name
git config --global user.email

3. Criando um projeto e iniciando o repositório

Crie uma pasta para o projeto e, dentro dela, crie um arquivo chamado index.html. Abra o terminal nessa pasta. O terminal precisa estar no diretório correto para que os comandos atuem no projeto esperado.

Para conferir a pasta atual, no PowerShell use pwd. Em seguida, inicialize o repositório Git:

git init

Esse comando cria a estrutura interna do repositório, normalmente na pasta oculta .git. A partir desse momento, o Git pode manter o histórico de versões dos arquivos desse projeto.

Atenção: git init não envia arquivos para a internet nem cria, por si só, um repositório no GitHub. Ele inicializa um repositório local no computador.

4. Consultando o estado do projeto: git status

O comando git status é uma das principais ferramentas de consulta. Ele informa em qual branch o repositório está, quais arquivos ainda não são rastreados e quais arquivos têm alterações pendentes ou preparadas para o próximo commit.

git status

Um arquivo recém-criado pode aparecer como untracked (não rastreado). Isso significa que o Git ainda não o incluiu no controle de versão. Um arquivo rastreado que foi editado pode aparecer como modificado.

5. A área de preparação: Staging Area

O Git separa as alterações em etapas. A área de preparação, também chamada de stage ou index, permite selecionar o que entrará no próximo commit. Pense nela como uma caixa na qual são colocadas as alterações que serão registradas juntas.

Para adicionar um arquivo específico à área de preparação:

git add index.html

Para adicionar arquivos novos e modificados do diretório atual e de seus subdiretórios:

git add .

Use git status novamente para conferir o resultado. Antes de usar git add ., verifique quais arquivos foram modificados, para evitar preparar arquivos que não deveriam fazer parte do commit.

6. Registrando uma versão: git commit

Um commit registra uma versão do conteúdo que está na área de preparação. A mensagem deve resumir a alteração de forma clara e específica.

git commit -m "Cria a estrutura inicial do index.html"

A opção -m permite escrever a mensagem diretamente no comando. O commit registra o conteúdo preparado naquele momento; salvar o arquivo no editor, por si só, não cria um commit.

Depois do commit, execute git status. Se não houver novas alterações, o Git normalmente informará que a árvore de trabalho está limpa (working tree clean).

7. Consultando o histórico: git log

O histórico registra os commits do repositório. Para consultar os detalhes, execute:

git log

Cada registro pode mostrar o identificador do commit, a autoria, a data e a mensagem. Para uma visualização resumida, use:

git log --oneline

O identificador, chamado hash, é uma sequência de caracteres que identifica aquele commit. Ele permite referenciar um registro específico do histórico.

Como sair da visualização do histórico

Em muitos terminais, git log abre um paginador: uma tela que permite ler a saída em partes. Para sair e voltar ao prompt do terminal, pressione a tecla q. Isso encerra apenas a visualização; não apaga nem modifica o histórico.

Dentro desse tipo de visualização, a barra de espaço avança uma página e as setas podem mover a leitura linha a linha. Os atalhos podem variar conforme o paginador e o terminal utilizado.

8. Entendendo HEAD e main

O HEAD é uma referência que indica a posição atual de trabalho no histórico. Em um repositório simples, é comum ver algo como HEAD -> main: isso indica que o HEAD está apontando para o commit atual da branch chamada main.

Uma branch é uma linha de desenvolvimento. main é um nome comum para a branch principal, mas o nome pode variar de um projeto para outro. O texto exibido no terminal depende do estado atual do repositório.

9. Continuando o projeto: modificar o HTML

Com o primeiro commit criado, a próxima etapa é fazer uma alteração real e comparar o estado atual do arquivo com a última versão registrada. O objetivo é entender que o Git não apenas guarda versões: ele também permite examinar exatamente o que mudou.

  1. Abra o arquivo index.html no editor de código.
  2. Altere o texto do elemento <title> para Meu primeiro projeto com Git.
  3. Dentro do <body>, adicione um título e um parágrafo, por exemplo:
<h1>Meu primeiro projeto com Git</h1>
<p>Esta página está sendo versionada com Git.</p>

Salve o arquivo no editor. Salvar o arquivo altera o conteúdo na pasta, mas ainda não cria um commit.

Agora consulte o estado do repositório:

git status

O arquivo index.html deverá aparecer como modificado, desde que já tenha sido incluído em um commit anterior. Em seguida, visualize as diferenças:

git diff

10. Lendo a saída de git diff

O comando git diff, sem opções adicionais, mostra as diferenças entre as alterações atuais ainda não preparadas e a versão que está na área de preparação. Se as alterações ainda não foram preparadas com git add, o comando normalmente mostra o que mudou em relação ao conteúdo preparado — que, nesse caso, corresponde ao último commit.

Na saída do git diff, observe os sinais no início das linhas:

  • - indica uma linha removida da versão comparada.
  • + indica uma linha adicionada na versão comparada.
  • Linhas sem esses sinais podem aparecer como contexto, para ajudar a localizar a mudança.

O cabeçalho de cada bloco também informa o arquivo comparado e a região aproximada em que ocorreram as mudanças. O Git mostra diferenças de conteúdo; ele não explica automaticamente a intenção da alteração.

Como sair da tela do git diff

Quando a saída é longa, o Git pode abri-la em um paginador, em vez de devolver imediatamente o prompt. Para sair dessa tela e retornar ao terminal, pressione q. Isso apenas fecha a visualização; não desfaz alterações nem encerra o Git.

Atalhos comuns do paginador:

  • q: sair da visualização.
  • Espaço: avançar uma página.
  • b: voltar uma página, quando suportado.
  • ↑ e ↓: mover a leitura linha a linha, quando suportado.

Como visualizar a saída inteira sem abrir o paginador

Para imprimir a saída diretamente no terminal, sem o paginador configurado pelo Git, use:

git --no-pager diff

O terminal exibirá a saída contínua. Se houver muitas linhas, parte do conteúdo pode ficar acima da área visível; role para cima no terminal para consultar o que já foi impresso. Em terminais integrados, a quantidade de histórico disponível depende das configurações de rolagem.

Para conferir as alterações que já foram preparadas com git add, use:

git diff --staged

Para comparar todas as alterações em arquivos rastreados com o último commit — incluindo as alterações preparadas e as ainda não preparadas — use:

git diff HEAD

Importante: arquivos novos que ainda não foram rastreados normalmente não aparecem no git diff. Para que o Git passe a comparar um arquivo novo, primeiro adicione-o à área de preparação com git add nome-do-arquivo. Isso não cria um commit; apenas prepara o arquivo.

11. Revisar antes de registrar

Antes de criar um novo commit, confira o estado e leia as diferenças. Essa revisão ajuda a detectar texto removido por engano, alterações incompletas e arquivos que não deveriam entrar no registro.

git status
git diff

Se as alterações estiverem corretas, prepare o arquivo:

git add index.html

Confira o que foi preparado:

git diff --staged

Se o conteúdo preparado estiver correto, crie o próximo commit:

git commit -m "Atualiza o conteúdo inicial da página"

Por fim, confira o estado e o histórico:

git status
git log --oneline

12. Resumo dos comandos apresentados

  • git --version: verifica a versão instalada do Git.
  • git config --global: configura dados padrão de autoria.
  • git init: inicializa um repositório local.
  • git status: mostra o estado atual dos arquivos e da área de preparação.
  • git add: prepara arquivos para o próximo commit.
  • git commit -m "mensagem": registra as alterações preparadas.
  • git log e git log --oneline: consultam o histórico.
  • git diff: mostra alterações ainda não preparadas.
  • git diff --staged: mostra alterações preparadas.
  • git diff HEAD: compara alterações em arquivos rastreados com o último commit.
  • git --no-pager diff: mostra a saída do diff sem abrir o paginador.

O fluxo praticado nesta etapa é: editar os arquivos, conferir com git status, examinar as mudanças com git diff, preparar o que deve ser registrado, revisar com git diff --staged e então criar o commit. Esse processo torna o histórico mais compreensível e reduz o risco de registrar alterações indesejadas.

13. Documentando o projeto: README.md

Até aqui, o projeto contém uma página HTML e um histórico de versões. Agora vamos adicionar dois arquivos comuns em projetos de desenvolvimento: o README.md e o .gitignore. Crie os arquivos na mesma pasta em que está o index.html, dentro do repositório Git.

O que é o README?

O arquivo README.md é a apresentação e a documentação inicial do projeto. Ele explica, por exemplo, qual é o objetivo do projeto, quais arquivos fazem parte dele, como abrir ou executar o conteúdo e quais ferramentas são necessárias. A extensão .md significa Markdown, um formato de texto simples que permite criar títulos, listas, links e trechos de código.

Crie um arquivo chamado README.md e escreva um conteúdo semelhante ao exemplo abaixo. Adapte o texto ao projeto que está sendo desenvolvido.

# Projeto de Página Web

## Objetivo
Projeto de estudo para praticar HTML e aprender os fundamentos do Git.

## Arquivos
- index.html: página web principal.
- README.md: documentação e apresentação do projeto.
- .gitignore: lista de arquivos que o Git deve ignorar.

## Como visualizar
Abra o arquivo index.html em um navegador.

Salve o arquivo. O README ajuda outra pessoa — ou você mesmo no futuro — a entender rapidamente o propósito do projeto, sem precisar analisar todos os arquivos primeiro.

14. O que é o .gitignore?

O arquivo .gitignore informa ao Git quais arquivos ou pastas devem ser ignorados quando ainda não estão sendo rastreados pelo repositório. Ele é útil para evitar que arquivos temporários, cache, configurações locais, dependências instaladas ou informações privadas sejam adicionados por engano ao histórico.

Crie um arquivo chamado exatamente .gitignore, sem extensão adicional. Em alguns editores do Windows, confira se o nome não foi salvo acidentalmente como .gitignore.txt.

Exercício: ignorando o README para observar o comportamento do Git

Para demonstrar como as regras funcionam, adicione temporariamente a seguinte linha ao arquivo .gitignore:

README.md

Essa regra pede ao Git para ignorar um arquivo com esse nome. Salve o .gitignore e execute:

git status

Observe que o README.md pode não aparecer como arquivo não rastreado, enquanto o .gitignore deverá aparecer como novo arquivo. Para confirmar qual regra está fazendo o Git ignorar o README, execute:

git check-ignore -v README.md

O comando apresenta o arquivo de regras e a linha responsável por ignorar o README.

Observação importante: normalmente, não ignoramos o README

Esta regra é apenas um exercício de demonstração. Em projetos reais, normalmente queremos versionar o README.md, porque a documentação deve acompanhar o código e ficar disponível para quem acessar o repositório. O .gitignore costuma ser usado para outros arquivos, como os exemplos abaixo:

# Arquivos temporários do sistema operacional
.DS_Store
Thumbs.db

# Cache e arquivos temporários do Python
__pycache__/
*.py[cod]

# Ambientes virtuais Python
.venv/
venv/

# Arquivos locais de configuração com segredos
.env

Esses exemplos são comuns em diferentes tipos de projeto, mas o conteúdo ideal depende das linguagens, ferramentas e arquivos realmente usados. Não adicione uma regra só porque ela aparece em um exemplo: entenda primeiro o que ela ignora.

Removendo a regra de demonstração

Como queremos manter a documentação no histórico deste projeto, abra o .gitignore e remova a linha README.md. Você pode manter as outras regras que fizerem sentido para o projeto. Salve o arquivo e execute novamente:

git status

Agora o README.md deverá aparecer como arquivo não rastreado, desde que ainda não tenha sido adicionado a um commit. Se ele continuar ignorado, confira se existe outra regra aplicável no próprio .gitignore, em regras globais ou em outro arquivo de exclusão.

15. Preparando e registrando os novos arquivos

Antes de preparar os arquivos, confira o estado do repositório. Depois, adicione o README e o .gitignore à área de preparação e examine o que será registrado:

git status
git add README.md .gitignore
git status
git diff --staged

Leia a saída de git diff --staged. Verifique se o README contém a documentação pretendida e se o .gitignore contém apenas regras adequadas. Se a saída estiver aberta em um paginador, pressione q para sair. Se precisar imprimir a saída diretamente no terminal, use git --no-pager diff --staged.

Quando a revisão estiver concluída, registre os arquivos em um commit:

git commit -m "Adiciona documentação e regras de arquivos ignorados"

Por fim, confira se o repositório está limpo e consulte o histórico:

git status
git log --oneline

O objetivo desta etapa é praticar a documentação do projeto, compreender como o Git ignora arquivos e revisar as alterações antes de registrá-las. O README normalmente deve ser versionado; o .gitignore serve para evitar que arquivos que não devem fazer parte do histórico sejam adicionados por engano.
